# Phase 2A — Property listing approval

Implemented locally; no deployment or production record changes.

## Behavior

- New owner/admin-created sale and rental listings receive `moderationStatus: pending_review`. The existing `status: active/inactive` remains the archive flag.
- Administrators approve, reject, or request changes through the existing property details dialog. Rejection/change requests require a trimmed reason (maximum 2,000 characters).
- Owners see their submission state and review reason in Manage Property. Editing listing content resubmits for review; rejected/change-requested submissions can also be explicitly resubmitted.
- Listing content edits, including edits to approved listings, remove public visibility until approval. Tenancy operations and archive/restore retain the moderation state.
- Public lists, search, details and managed cover-photo delivery share the approval/publication policy. `all=true` cannot bypass it. Pending/private records remain available to authorized owners, administrators and existing property members.
- New offers require a published listing; visit/enquiry requests for private records require existing membership. Existing member workflows remain available.
- Moderation transitions use Firestore transactions, persisted roles and revision checks. Each submission/decision records actor UID, timestamp, action and revision; decisions retain reasons. Stale/concurrent decisions return 409. Client-provided moderation metadata and mixed decision/content updates are rejected.
- Tenant-submitted records retain `ownershipVerification` and remain private. They cannot enter public listing moderation.

## Legacy compatibility strategy

An absent `moderationStatus` means legacy approval eligibility **at read time only**. Normal publication rules still require an active, non-archived sale/rental listing that is not tenant-supplied, sold or rented. Explicit unknown/null moderation states fail closed. No timestamp cutoff, production backfill or automatic record migration is used.

Legacy archive/restore preserves that eligibility. The first listing-content edit persists an explicit pending state and submission history; an administrator must then approve it. Any future explicit legacy approval backfill requires a separately reviewed inventory and authorization. Historical public storage URLs are not revoked by this workflow.
